# Рецепты, готовка впрок и дневник

**Статус.** Согласованная цель MVP для первого запуска. Действующий Nutrition уже хранит приёмы пищи как собственные JSONB-снимки, считает итоги и публикует их через outbox. Импорт рецепта, чтение фактов по позициям плана и описанные ниже взаимодействия ещё предстоит реализовать. [ADR 0014](../adr/0014-autonomous-nutrition-service.md) · [активный API](../../contracts/openapi/public/nutrition.yaml) · [физическая схема](../../contracts/dbml/nutrition.dbml) · [проектный API](../../contracts/openapi/planned.yaml).

## Кто отвечает за каждый факт

| Вопрос | Владелец и ключ | Что фиксируется |
|---|---|---|
| По какому рецепту? | Recipe, `recipeId + recipeVersion + variantId + excludedLineIds` | Опубликованная редакция, авторский вариант, исключённые необязательные строки. Один состав определяет шаги, аллергены, количества для покупки и КБЖУ. |
| Сколько приготовить и куда распределить? | Meal Planner, `plannedCookId` и `planItemId` | У готовки есть дата, выбор Recipe, положительный масштаб ингредиентов и ожидаемый выход. Каждый приём ссылается на одну готовку того же плана и задаёт количество с единицей. |
| Что получилось? | Recipe, `cookingSessionId` | Выбор и масштаб входных ингредиентов фиксируются при старте. Завершение фиксирует положительный фактический выход. Связь с плановой готовкой необязательна. |
| Сколько съели? | Nutrition, `mealId + dishId` | Собственная копия состава и выхода, фактическое количество, дата и КБЖУ. Для еды по плану есть `planItemId`. |
| Что купить? | Shopping, `cartId` и при импорте `plannedCookId` | Снимок покупных ингредиентов на одну готовку, затем локальные поправки корзины. |
| Каковы нутриенты продукта? | Food Catalog, ID и версия пользовательского продукта или штрихкод внешнего источника | Имя, бренд, г/мл, значения на 100 и известная мера штуки. Open Food Facts доступен через временный кэш. Recipe фиксирует редакционный источник при публикации. Nutrition сохраняет свою базу при записи. |

[Recipe](../../contracts/dbml/recipe.dbml) · [Meal Planner](../../contracts/dbml/meal-planner.dbml) · [Shopping](../../contracts/dbml/shopping.dbml) · [Food Catalog](../../contracts/dbml/food-catalog.dbml).

Каждый рецепт можно масштабировать. Если в рационе Pro известно предпочтение готовить впрок, Planner повышает вес редакционного тега пригодности для meal prep среди кандидатов, прошедших ограничения рациона. Это не меняет схему блюда. Учёт домашних запасов, отдельный учёт остатков, личные редакции и свободная сборка из произвольных продуктов выходят за рамки MVP. Избранное и обратная связь относятся к карточке.

## Один выбор от публикации до дневника

Редакция неизменяема после публикации. У неё минимум один вариант и ровно один вариант по умолчанию. Ключ строки уникален, исключения принадлежат выбранному варианту. Два вхождения одного ингредиента в разные слои имеют разные ключи. Зависимый шаг привязан к необязательной строке своего варианта. Если вариант меняет технологию, автор задаёт ему собственные шаги. Новый вес, публикация или изменение этикетки не меняют уже зафиксированные значения.

У листовой строки есть форма продукта, положительное количество в базовых г/мл, источник, КБЖУ на 100 и аллергены на момент публикации. Для показа после подготовки допустима вторая пара «количество, единица». Для заготовки строка ссылается на конкретный опубликованный вариант с количеством в единицах его выхода. В MVP допускается один уровень заготовок. При публикации проверяются глубина и отсутствие циклов. Recipe раскрывает заготовку пропорционально использованной доле, сохраняя происхождение строк. В сумме КБЖУ и покупок учитываются её листовые ингредиенты один раз. Если пользователь указывает в корзине, что заготовка уже готова, исключается только её вклад в покупку, состав блюда сохраняется.

Для выбранной конфигурации Recipe вычисляет выход и рекомендуемую порцию, масштабирует входные строки, собирает шаги и пересчитывает КБЖУ и аллергены после исключений. Масса входных ингредиентов сама по себе не даёт массу выхода. Для конфигурации с изменившимся выходом нужен измеренный выход или проверенное автором правило. До этого соответствующая комбинация и единица записи недоступны. Редакционный итог варианта применяется к его полному составу.

### Внутренний ответ Recipe

Потребитель передаёт точный выбор или ID завершённой готовки с контекстом аккаунта. Для каталога масштаб исходного рецепта равен 1, для сессии берётся фактический масштаб входа. Recipe возвращает выбранный состав и **базу для деления**. Для сессии это фактический выход. Потребитель не должен повторно масштабировать уже пересчитанные количества. Пример ответа с одной строкой для проверки арифметики (значения синтетические, UUID сокращены для чтения).

```json
{
  "selection": {"recipeId":"r1","recipeVersion":2,"variantId":"v1","excludedLineIds":[]},
  "cookingSessionId":"c1",
  "title":"Фруктовые полоски",
  "ingredientScale":1,
  "basisYield":{"value":12,"unit":"PIECE"},
  "serving":{"value":2,"unit":"PIECE"},
  "lines":[{"lineId":"l1","ingredientId":"i1","layer":"основа","name":"Фруктовое пюре",
            "input":{"value":300,"unit":"G"},"state":"пюре","source":"проверенная этикетка",
            "nutritionPer100":{"calories":60,"proteinG":1,"fatG":0,"carbsG":14,"fiberG":null},
            "allergens":[]}],
  "steps":[{"position":1,"text":"Высушить и нарезать полосками"}],
  "nutritionTotal":{"calories":180,"proteinG":3,"fatG":0,"carbsG":42,"fiberG":null}
}
```

У вложенной заготовки сохраняй путь от родительской строки до листа. Для Shopping он позволяет опустить покупку сырья одной готовой начинки до агрегации общих ингредиентов. Удобные экранные единицы «пакетик», «полоска» и «батончик» описывают штуку конкретного варианта. Пересчёт между г, мл и штуками допустим при известной измеренной базе. Для равных штук в партии достаточно соотношения штук. Стандартная порция — заданное автором количество единиц выхода.

## План и покупки

Мобильный клиент читает план через публичный API, извлекает ID видимых приёмов и запрашивает факты Nutrition пачками до 100 ID через gateway. Объединяет ответы по `planItemId`, без связи по названию, дате или рецепту. У одного приёма может быть несколько фактов. Для сводки дня используется фактическое время еды. Плановая карточка показывает факты один раз, еда без назначения остаётся доступной в дневнике. При недоступном чтении показывается неизвестный статус выполнения. Planner не хранит копию факта и не получает события расхода.

Замена одного приёма создаёт новое назначение для него и отдельную плановую готовку, когда меняется выбор. Старые факты не перепривязываются к новому назначению. Соседние приёмы из прежней готовки и готовые покупки сохраняются. Для записи факта с привязкой Nutrition проверяет у Planner владельца и соответствие назначения выбору рецепта, а для плановой сессии также ID готовки. Recipe проверяет у Planner владельца и выбранный состав перед стартом плановой сессии. Эти точечные чтения не вызывают обратного разрешения рецепта. Проверки выполняются до локальной транзакции. Контракты будущих вызовов требуют workload identity, разрешение получателя и контекст аккаунта. [Целевые вызовы](model/sync-calls.yaml).

В предпросмотре и импорте диапазон дней выбирает назначения, затем Planner собирает **различные ID готовок** и передаёт Shopping их выбор и полный объём. Например, готовка на четыре порции входит целиком, даже если один из выбранных дней использует только одну порцию. Shopping раскрывает покупные ингредиенты, агрегирует только совместимые базовые единицы. Задача импорта закреплена за аккаунтом и ключом запроса. Повтор с тем же телом возвращает ту же задачу, изменённое тело с тем же ключом конфликтует. Уникальность пары «корзина, плановая готовка» защищает и от параллельных импортов перекрывающихся диапазонов. Уже добавленная строка сохраняет ручные правки. Два разных ID готовки одного блюда дают два набора. Прямое добавление из каталога имеет свой ID позиции и не требует ID плана. Отметка «уже есть» и изменение порций действуют в корзине. Источником изменения закупки служит явное действие пользователя.

## Задачи автора Nutrition

1. Реализовать проектный `POST /diary/recipe` по завершённой готовке своего аккаунта или по опубликованному выбору из каталога. Приём пищи может быть вне плана. Для записи нужны фактические количество и единица, `clientGeneratedId`, `eatenAt`, согласованные `localDate` и IANA `timezone`. У новой записи статус 201, у точного повтора 200, у конфликта версии или ключа 409.
2. Расширить документ блюда и транспортные модели. В JSONB сохранить принадлежность строк редакционному ингредиенту, исходную базу и выход, выбранный состав, съеденное количество и итог. Например, в снимке выше для двух полосок доля равна 2/12, пюре в факте 50 г, итог 30 ккал. Сохранённая база по-прежнему содержит 300 г и выход 12. Импорт не должен маскировать редакционную строку как пользовательский продукт. Проверить, что развёрнутый состав помещается в пределы ADR 0014 (до 100 строк на блюдо).
3. Проверить повтор команды по аккаунту и хешу **исходного запроса** до обращения к зависимостям. Получить снимок и проверить необязательную плановую связь вне транзакции. Под существующей блокировкой повторить проверки аккаунта, tombstone и идемпотентности, записать документ и outbox атомарно. Точный повтор успешной записи работает при недоступном Recipe. Первая неудачная попытка не создаёт meal. Ручная запись и сохранённые блюда остаются автономными.
4. Добавить изменение количества с версией блюда. Пересчитывать строки из сохранённой базы, затем блюдо, приём и день одной транзакцией. Сохранять корректные ID строк, десятичную арифметику, округление до трёх знаков, неизвестные макросы и десятичные строки КБЖУ в HTTP. Проверить конкурентную правку и удаление. **Открытый вопрос ревью:** если пользователь вручную редактировал отдельную строку, как обозначить базу дальнейшего масштабирования? До решения безопасный ответ на конфликт — сообщить о несовместимой правке и сохранить введённые данные.
5. Добавить пакетное чтение действующих фактов своего аккаунта по `planItemId`, независимо от даты еды. Проверить пустой результат, несколько записей, перенос дня и удаление. Нельзя раскрыть чужой ID по ответу. При исправлении и удалении переиспользовать текущие правила событий Nutrition. Реализацию, миграции при доказанной необходимости, активный OpenAPI и тесты доставит автор Nutrition отдельным PR.

## Ревью схем и контрактов остальных сервисов

| Где | Что должен доказать пример |
|---|---|
| Recipe | Версия и вариант воспроизводимы. Исключение затрагивает ровно одну строку и нужные шаги. Итог КБЖУ, аллергены, выход и покупные строки согласованы. Заготовка не создаёт цикл и не удваивает вклад. Избранное и обратная связь сохраняются на карточке. |
| Meal Planner | По схеме различимы одна готовка на несколько дней и две готовки одного рецепта. Замена не меняет соседние назначения. Недоступный дневник не превращается в статус «не съедено». |
| Shopping | Повтор ключа, параллельный импорт перекрывающихся дней, изменение плана и ручная правка корзины дают предсказуемое количество. Начинка, уже имеющаяся дома, не вычитает сырьё других блюд. |
| Food Catalog | Этикетка, пользовательский продукт или кэш могут измениться после публикации. КБЖУ старой готовки и дневника воспроизводятся по снимку. Нет неявного перевода мл в г. |
| Между сервисами | Везде различимы версия рецепта, вариант, плановая и фактическая готовки, назначение и версия блюда дневника. Чужие записи недоступны. Владельцы меняют только свою БД. Пищевой факт появляется по явному подтверждению. |

## Приёмочные примеры

- **Рис и начинка.** 300 г сухого риса идут в покупку и в расчёт по этикетке сухого продукта. 700 г готового у той же строки используются в шаге. Если буррито требует 200 г белковой начинки из рецепта с выходом 800 г, вклад равен четверти её состава. При наличии готовой начинки в покупку идут только остальные компоненты буррито. В дневник попадает съеденная доля всего буррито.
- **Такитос.** Полный состав рассчитан на 27 штук, при масштабе 1 получилось 24 равные штуки. В плане 2 на понедельник и 4 на среду из одной готовки. При записи 3 в понедельник доля равна 3/24, при исправлении на 2 — 2/24. При удалении исчезает только факт. Выход 24, оба назначения и покупка одной партии сохраняются. Запись трёх штук из каталога без готовки использует 3/27.
- **Спортивные перекусы.** Манго с яблоком и ягоды — варианты одной пастилы, у каждого собственный выход после сушки. Две из 12 равных полосок — 2/12 КБЖУ выбранного состава. Аналогично учитываются пакетики геля и батончики. При неодинаковых штуках можно использовать измеренную массу или объём партии и порции.
- **Слои.** В овсянке исключение верхнего банана сохраняет банан в основе. При выборе говядины в буррито меняются мясо, вес, зависимые шаги и КБЖУ. План, карточка, корзина и дневник получают один выбор. Позднейшая редакция не меняет прежний снимок.
